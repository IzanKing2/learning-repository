    Programar con IA, paso a paso

    Una guía para montar un proyecto en el que tú decides qué se construye y la IA escribe el código. No hace falta saber programar para empezar: hace falta orden.

    Cómo usar esta guía. Ve paso a paso, sin saltarte ninguno. Cada paso tiene dos listas: «Hazlo» (lo que tienes que hacer) y «Comprueba» (cómo saber que ha quedado bien). Tus marcas se guardan en este navegador, así que puedes cerrar y volver cuando quieras.

    Si usas el plan gratuito u otra IA Por qué importa Paso completado
    Mini diccionario (léelo antes de empezar)
    Agente de IA
    Una IA que no solo conversa: lee tus archivos, escribe código, ejecuta comandos y hace cambios por ti.
    Repositorio (repo)
    La carpeta del proyecto con todo su historial de cambios. Vive en GitHub (en internet) y en tu ordenador.
    Clonar
    Descargar el repositorio de GitHub a tu ordenador, conectado para poder subir cambios.
    Commit
    Un «punto de guardado» con una frase que explica qué cambió. Si algo se rompe, puedes volver a cualquier commit anterior.
    Rama (branch)
    Una copia paralela del proyecto para probar algo sin tocar la versión buena (llamada main).
    Pull request (PR)
    Una petición para unir una rama a main, revisando antes los cambios.
    Terminal
    La ventana donde se escriben comandos. Con agentes de IA casi siempre los escribe la IA y tú solo apruebas.
    Conector (MCP)
    Un «enchufe» que deja a la IA usar otro servicio: GitHub, Vercel, Supabase…
    Skill
    Un manual de instrucciones que la IA lee cuando hace un tipo de tarea concreto. Es una carpeta con un archivo SKILL.md.
    Spec
    Especificación: un documento que describe qué debe hacer una parte del programa y cómo saber si funciona. Se escribe antes del código.
    CLAUDE.md / AGENTS.md
    El archivo de normas del proyecto. Es lo primero que lee el agente cada vez que empieza a trabajar.

    Prepara cuentas y herramientas

    Antes de nada, necesitas dónde guardar el proyecto, dónde editarlo y con qué IA trabajar.

    Qué necesitas

    • Cuenta de GitHub (gratis): donde vivirá el proyecto. github.com/signup
    • Cuenta de Claude: claude.ai.
    • Git: el programa que guarda el historial. Descárgalo de git-scm.com. Si prefieres no usar la terminal, instala también GitHub Desktop.
    • Un editor de código: VS Code es gratis y el más usado.
    • Un agente de IA que trabaje dentro de tu proyecto (mira la tabla).
    HerramientaCostePara qué
    Claude CodePlan Pro o superiorEl agente de Claude. Es la opción recomendada: sigue muy bien las normas del proyecto, usa skills y conectores, y trabaja de forma ordenada en tareas largas.
    Claude (chat web)Gratis, con límitesPensar, escribir specs, revisar ideas. No toca tus archivos directamente.
    Antigravity, Gemini CLI, GitHub Copilot…Tienen modalidades gratuitasAgentes alternativos. Todo lo de esta guía (normas, skills, specs, docs) sirve igual con ellos.
    Plan gratuitoClaude Code no está incluido en el plan gratuito de Claude. Combinación recomendada si no pagas: usa el chat de Claude para pensar y escribir las specs, y un agente con modalidad gratuita para ejecutar en tu ordenador. La clave de esta guía no es la herramienta, es el método: si el proyecto está bien documentado, cualquier IA trabaja bien en él.

    Configura los conectores

    Dale a la IA acceso a los servicios que usará el proyecto, para que no tengas que copiar y pegar entre ventanas.

    Por qué importaCon el conector de GitHub, la IA puede leer tu código; con el de Vercel, publicar la web; con el de Supabase, crear la base de datos. Tú das la orden y ella hace las gestiones.

    Dónde están en Claude

    1. Entra en claude.ai y pulsa tu nombre o iniciales, abajo a la izquierda.
    2. Abre Configuración y busca la sección Conectores (en algunas versiones aparece dentro de «Personalizar»).
    3. Pulsa Explorar conectores (o el botón +) para ver el directorio completo.
    4. En cada servicio pulsa Conectar, inicia sesión en ese servicio y acepta los permisos.
    5. En un chat, pulsa + en la caja de texto → Conectores y activa los que quieras usar en esa conversación.

Si tu herramienta no tiene conectores, no pasa nada: el agente puede usar Git y las webs de cada servicio igualmente.
    SeguridadCuando un conector pida permisos, lee qué pide. Para empezar, deja activado que la IA te pregunte antes de hacer cambios.

    Crea el repositorio en GitHub

    El repositorio es la casa del proyecto: todo el código, la documentación y el historial de cambios.

    Público o privado

    PúblicoPrivado
    Quién lo veCualquier persona en internetSolo tú y quien invites
    Úsalo paraProyectos de portfolio, código abierto, cosas que quieres enseñarProyectos de clientes, ideas de negocio, cualquier cosa con datos o lógica que no quieras compartir
    CosteGratisGratis

    En la duda, privado. Puedes hacerlo público más adelante (Settings → Danger Zone → Change visibility); al revés, si ya lo ha visto alguien, no hay vuelta atrás.

    Cómo crearlo

    1. En GitHub, pulsa el + de arriba a la derecha → New repository.
    2. Repository name: nombre corto, en minúsculas y con guiones (ej. agenda-citas).
    3. Description: una frase sobre qué es.
    4. Elige Public o Private.
    5. Marca Add a README file.
    6. En .gitignore elige la plantilla de tu tecnología (ej. Node). Esto evita subir archivos que no deben subirse.
    7. Pulsa Create repository.

    Clona el repo y crea el CLAUDE.md

    Baja el proyecto a tu ordenador y escribe las normas que la IA seguirá siempre.

    Clonar

    1. En la página del repo pulsa el botón verde Code y copia la dirección HTTPS.
    2. Con GitHub Desktop: File → Clone repository, pega la dirección y elige carpeta.
    3. Con terminal: ve a tu carpeta de proyectos y escribe:
    git clone https://github.com/TU-USUARIO/agenda-citas.git
cd agenda-citas

    Abre esa carpeta en VS Code (File → Open Folder) y arranca tu agente dentro de ella.

    El CLAUDE.md

    Es el reglamento del proyecto. El agente lo lee al empezar cada sesión, así no tienes que repetirle cómo trabajar. Va en la raíz del proyecto (la carpeta principal).

    Truco: en Claude Code, el comando /init analiza el proyecto y crea un primer CLAUDE.md. Después lo ajustas con esta plantilla:

    CLAUDE.md (plantilla inicial)
    # Proyecto: [nombre]

## Qué es
[Una o dos frases: qué hace la aplicación y para quién es.]

## Tecnologías
- [Ej: Next.js, Supabase, desplegado en Vercel]

## Cómo trabajar en este proyecto
- Antes de programar algo, lee la spec correspondiente en /specs.
- Si no existe spec para lo que te pido, propónmela primero y espera mi aprobación.
- Trabaja en tareas pequeñas. Al terminar cada una, resume qué has cambiado.
- No borres archivos ni instales dependencias nuevas sin preguntarme.
- Nunca escribas claves o contraseñas en el código: usa variables en .env.
- Si algo no está claro, pregunta antes de suponer.

## Documentación que debes mantener al día
- SPECS.md: índice de funcionalidades y su estado.
- DESIGN.md: diseño visual y decisiones de interfaz.
- docs/decisions/: una nota por cada decisión importante (qué, por qué, alternativas).
- CHANGELOG.md: resumen de cambios por versión.

## Tests
- Cada funcionalidad nueva lleva sus tests.
- Antes de dar algo por terminado, ejecuta los tests y dime el resultado.

## Commits
- Mensajes en español con formato: tipo: descripción corta
  (tipos: feat, fix, docs, test, refactor, chore).
- Un commit por cambio lógico. Nunca subas directamente a main.

## Skills
[Se rellena en el paso 5]
    Si usas otra IACada agente busca su archivo de normas con un nombre propio (CLAUDE.md, AGENTS.md, GEMINI.md…). AGENTS.md es el estándar que entienden cada vez más herramientas. Mantén un único contenido y pide a la IA: «crea un AGENTS.md que diga que las normas están en CLAUDE.md» (o al revés). Así cualquier IA que entre al proyecto sabe cómo trabajar.

    Añade skills para tu proyecto

    Las skills son manuales especializados: la IA los consulta solo cuando hace ese tipo de tarea.

    Diferencia con el CLAUDE.mdEl CLAUDE.md son normas generales que se leen siempre. Una skill es un manual concreto («cómo diseñamos pantallas», «cómo escribimos tests») que solo se carga cuando hace falta. Así la IA no se satura de instrucciones.

    Cómo encontrar skills útiles

    Pide recomendaciones a otra IA (ChatGPT, el chat de Claude…) describiendo tu proyecto. Copia este mensaje:

    Mensaje para pedir recomendaciones
    Voy a desarrollar [describe el proyecto en 2-3 frases] usando [tecnologías].
Trabajo con agentes de IA y skills (carpetas con un SKILL.md).
Recomiéndame 5-8 skills útiles para este proyecto. Para cada una dime:
- nombre
- para qué sirve
- si existe ya en algún repositorio público (con enlace) o si debo crearla.
No inventes enlaces: si no estás seguro de que exista, dilo.

    Busca también en el repositorio oficial de skills de Anthropic en GitHub (anthropics/skills) y revisa siempre una skill antes de instalarla: es un texto que la IA va a obedecer.

    Crear tu propia skill

    Una skill es una carpeta con un archivo SKILL.md. La recomendada para empezar es una de coherencia visual, para que todas las pantallas se vean iguales:

    .claude/skills/consistencia-visual/SKILL.md
    ---
name: consistencia-visual
description: Reglas de diseño del proyecto (colores, tipografía, espaciados, componentes). Úsala siempre que crees o modifiques cualquier pantalla o componente visual.
---

# Consistencia visual

## Colores
- Principal: #XXXXXX (botones y enlaces)
- Fondo: #XXXXXX
- Texto: #XXXXXX
- Error: #XXXXXX

## Tipografía
- Fuente: [nombre]
- Títulos: [tamaño y grosor]
- Texto normal: [tamaño]

## Componentes
- Usa siempre los componentes de /components antes de crear uno nuevo.
- Botones: esquinas redondeadas de 8px, altura mínima 44px.

## Reglas
- No inventes colores nuevos: usa solo los de esta lista.
- Toda pantalla debe verse bien en móvil.
- Si necesitas algo que no está aquí, pregúntame y actualiza este archivo.

    Lo más importante es la línea description: la IA decide si usa la skill leyendo esa frase. Escríbela diciendo cuándo usarla.

    Dónde se instalan

    • Dentro del proyecto (recomendado): .claude/skills/[nombre]/SKILL.md. Así viajan con el repositorio y cualquiera que lo clone las tiene.
    • En el chat de Claude: Configuración → Capacidades (o Personalizar) → Skills → subir la carpeta comprimida en .zip. Necesita tener activada la ejecución de código.

    Escribe las specs antes del código

    Primero se decide qué se construye; después se construye. Es el paso que más tiempo ahorra.

    Por qué importaUna IA sin specs rellena los huecos inventando. Con specs claras, sabe exactamente qué hacer y tú sabes exactamente qué comprobar. A esto se le llama Spec-Driven Development: la especificación manda y el código la cumple.

    Cómo hacerlo con la IA

    1. Deja que la IA te entreviste. No le pidas el plan directamente; pídele que te pregunte.
    2. Escribe los documentos base con lo que salga de la entrevista.
    3. Divide en specs por funcionalidad, cada una con criterios de aceptación.
    4. Revisa y aprueba cada spec antes de pasar al paso 7.
    Mensaje para empezar
    Quiero hacer [idea en 2-3 frases].
Antes de escribir nada, hazme preguntas una a una para entender bien
qué necesito: usuarios, funcionalidades, qué es imprescindible y qué puede
esperar, diseño y límites. Cuando lo tengas claro, propón:
1. SPECS.md con la lista de funcionalidades priorizadas.
2. DESIGN.md con el estilo visual.
3. Una spec por funcionalidad en /specs con criterios de aceptación.

    Qué documentos debes tener

    ArchivoQué contiene
    SPECS.mdVisión general: qué es la app, para quién, lista de funcionalidades con prioridad y estado (pendiente / en curso / hecha).
    DESIGN.mdEstilo visual, pantallas principales y cómo se navega entre ellas.
    specs/[funcionalidad].mdUna por funcionalidad: qué hace, pasos del usuario, casos raros, criterios de aceptación y lista de tareas.
    specs/reservar-cita.md (ejemplo de estructura)
    # Reservar cita

## Objetivo
El cliente puede reservar una cita libre desde el móvil en menos de un minuto.

## Flujo
1. Elige servicio.
2. Ve los huecos libres de los próximos 14 días.
3. Elige hueco, deja nombre y teléfono, confirma.

## Casos especiales
- Dos personas eligen el mismo hueco a la vez: solo la primera lo consigue.
- No hay huecos libres: mostrar mensaje y la siguiente fecha disponible.

## Criterios de aceptación
- [ ] No se puede reservar un hueco ya ocupado.
- [ ] El teléfono se valida antes de confirmar.
- [ ] El cliente ve una confirmación con fecha y hora.

## Tareas
- [ ] Tabla de citas en la base de datos
- [ ] Pantalla de selección de hueco
- [ ] Confirmación

    Genera el código, tarea a tarea

    Ahora sí: la IA programa. Tu papel es dirigir, revisar y probar.

    El ciclo de trabajo

    1. Elige una sola tarea de una spec. Nunca «hazme la app entera».
    2. Pide un plan primero. En Claude Code existe el modo plan (Shift+Tab): la IA explica qué hará sin tocar nada. Con otra IA, pídeselo: «explícame el plan y espera mi OK».
    3. Aprueba o corrige el plan.
    4. Deja que lo haga y lee el resumen de cambios.
    5. Pruébalo tú: abre la app y comprueba los criterios de aceptación.
    6. Commit (paso 9) y marca la tarea como hecha en la spec.
    Mensaje tipo
    Lee specs/reservar-cita.md. Vamos a hacer solo la tarea
"Pantalla de selección de hueco". Primero explícame el plan
y espera mi aprobación antes de tocar código.
    Conversaciones cortasCuando una conversación se alarga mucho, la IA empieza a olvidar detalles. Al terminar una tarea, empieza una conversación nueva (en Claude Code, /clear). Como todo está documentado, no se pierde nada.

    Mantén tests y documentación al día

    Es la memoria del proyecto. Sin ella, la siguiente IA (o tú en un mes) va a ciegas.

    • Tests: pequeños programas que comprueban automáticamente que todo sigue funcionando. Cada funcionalidad lleva los suyos. Pide: «ejecuta todos los tests y dime el resultado».
    • Specs actualizadas: si algo cambia mientras programáis, se cambia también en la spec.
    • Decisiones: cada decisión importante («usamos Supabase en vez de Firebase porque…») en una nota en docs/decisions/.
    • CHANGELOG.md: qué cambió en cada versión, en lenguaje sencillo.
    Mensaje al terminar cada tarea
    Antes de cerrar esta tarea:
1. Ejecuta los tests y dime si pasan.
2. Actualiza la spec y SPECS.md con el estado real.
3. Si hemos tomado alguna decisión importante, documéntala en docs/decisions/.
4. Añade el cambio al CHANGELOG.md.

    Consejo: añade esta lista al CLAUDE.md como «Definición de terminado». Así la IA lo hará sin que se lo pidas.

    Gestiona commits y ramas con la IA

    Guardar bien es lo que te permite deshacer cualquier error.

    Forma de trabajar

    1. Para cada funcionalidad, una rama nueva: «crea una rama para la funcionalidad reservar-cita».
    2. Al acabar cada tarea, commit: «revisa los cambios, muéstrame un resumen y haz commit con un mensaje claro».
    3. Al acabar la funcionalidad, pull request: «sube la rama y abre un pull request con resumen de cambios».
    4. Revisa el PR en GitHub y, si está bien, únelo a main (botón Merge).
    Ejemplos de buenos mensajes de commit
    feat: pantalla de selección de hueco
fix: no permitía reservar el último hueco del día
docs: decisión de usar Supabase para autenticación
test: tests de validación de teléfono
    Antes de aprobar un commitMira la lista de archivos que cambian. Si aparece un .env o algo que no esperabas, para y pregunta.

    Publica el proyecto

    Que la app esté en internet y se actualice sola con cada cambio.

    1. En Vercel, importa el repositorio de GitHub (o pídeselo a la IA con el conector).
    2. Añade las variables de entorno (las claves del .env) en la configuración del proyecto en Vercel, nunca en el código.
    3. Desde ese momento, cada vez que unas algo a main, la web se actualiza sola. Cada pull request genera además una versión de prueba con su propio enlace.
    Plan gratuitoVercel y Supabase tienen planes gratuitos suficientes para aprender y para proyectos personales. Revisa sus condiciones si el proyecto es comercial.

    Si algo sale mal

    Pasará. Con commits y documentación, nada es grave.

    • La IA da vueltas sin arreglarlo: para, abre una conversación nueva y explica el problema desde cero, señalando la spec.
    • Se ha roto algo que funcionaba: «vuelve los archivos al estado del último commit» o «revierte el commit X».
    • La IA ignora las normas: recuérdale «lee el CLAUDE.md» y, si se repite, haz esa norma más clara en el archivo.
    • No entiendes lo que ha hecho: «explícame este cambio como si no supiera programar». Nunca apruebes algo que no entiendes.
